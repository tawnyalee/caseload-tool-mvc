# CLAUDE.md — Action Manager App

## Project overview
Python/CustomTkinter desktop app, rewritten from a previous non-professional dev's spaghetti-code app into a clean MVC design. The app helps professors automate routine student communications (emails, texts, notes) and document them, organized into "Groups" (school courses).

The developer working on this is a C# developer who is newer to Python — favor clear, idiomatic Python and explain any non-obvious language features when they come up.

## Architecture
- `src/models/` — Action, Group, Student, EmailTemplate, and enum definitions
- `src/services/` — `ActionRepository`, `GroupRepository`, `TemplateRepository` (JSON file storage); `StudentDataProvider`, `EmailSender`, `TextSender`, `NoteWriter` (abstract interfaces with local `Fake*` implementations — real Salesforce/Cadence/Outlook adapters not built yet, see Known open items); `OutlookSignatureProvider`/`LocalOutlookSignatureProvider` (the one real, non-fake integration so far — lists actual Outlook signature names from `%APPDATA%\Microsoft\Signatures\`, used by both the Action editor and the ad-hoc email modal; `FakeOutlookSignatureProvider` exists for tests); `ActionRunner` (orchestrates running an action, welcome emails, or an ad-hoc send against students, with per-student failure isolation and logging — see Design decisions); `ActivityLogger` (writes to a daily log file and the Live Application Log panel from one call site); `html_richtext` (HTML ⇄ `tkinter.Text` WYSIWYG conversion, used by the template editor and the ad-hoc email compose modal)
- `src/views/` — `AddActionView`, `ScenarioNavPanel`, `DashboardView` (default startup view), `TemplateEditorModal`, `AdHocEmailModal`, and other CustomTkinter views
- `src/controllers/app_controller.py` — main app controller

## Working rules (follow these strictly)
1. **One focused change at a time.** Propose a single change with reasoning and a specific test to verify it, then wait for the result before moving on to the next thing.
2. **Always ask for the actual current code** before proposing changes to a file that's had prior edits — don't assume you remember its state; read the file fresh.
3. **Ask about intent (what SHOULD happen) vs. observed behavior** before proposing a fix — don't assume the cause.
4. **Preserve existing variable/field names and structures** unless they're actively misleading. Ask before renaming anything.
5. **ID-based lookups only.** Never write new code that looks up records (groups, templates, actions, or any future entity) by name — names can be renamed mid-session. Always use the record's stable ID.
6. **Name secondary issues, don't fix them.** If you spot an unrelated bug or issue while investigating something else, mention it but don't fix it until the current task is finished.
7. **Git safety net.** The developer is still learning Git. Proactively remind them when it's a good time to commit or branch (e.g. before starting a risky change, after a working milestone) — don't assume they'll remember to do it themselves. Also watch for real data files (`data/*.json`, `src/data/*.json`) picked up as "modified" from manual testing — confirm with the developer before including those in a commit; they're usually test noise, not intentional changes.

## Design decisions (settled — don't re-litigate without new input from the developer)
- **Resource access is abstracted behind interfaces** (`StudentDataProvider`, `EmailSender`, `TextSender`, `NoteWriter`), each with a local `Fake*` implementation backing everything today (`data/fake_students.json` plus in-memory records). Real Salesforce/Cadence/Outlook adapters implement the same interfaces later; nothing that calls them needs to change.
- **Running an action (`ActionRunner.run`):** email and text are attempted independently per student (one failing doesn't block the other). A note step — writing the interaction note *and* updating the student's roster-visible follow-up-note field, bundled as one unit — runs only if at least one communication succeeded; otherwise it's skipped and logged, not attempted. One student's failure never stops the run — every step (success/failure/skip) is logged via `ActivityLogger` and rolled into a final succeeded/failed/skipped summary.
- **Welcome emails (`ActionRunner.run_welcome_emails`, the Dashboard's "Send Welcome Emails" button):** deliberately no separate course/student-matching logic in the app. It just runs whichever action is marked as each group's `welcome_action_id` (already existing on `Group`) through `ActionRunner`, using whatever filter the professor configured on that action themselves. This was a deliberate simplification to avoid building course-mapping or "new student" detection logic in the app.
- **Dropped:** a "new students since last checked" dashboard count. Considered, then abandoned in favor of professors using their own filter criteria (e.g. "Follow Up Note Is Empty") on their welcome action — no local "last checked" state needed. Don't resurrect this without the developer asking.
- **Filters are NOT implemented yet.** `StudentDataProvider.get_students()` and everything downstream currently act on the full roster unconditionally — filters stored on an `Action` are not applied anywhere. The developer is still working out real-world filter requirements (field-type-aware operators, AND/OR grouping, relative dates, "Is Empty"/"Is Not Empty") from how they actually use Salesforce's own filters today. Don't design or guess at a filter engine without that input — ask.
- **Outlook signatures:** the "Select Outlook Signature" dropdown has no "None" option, on purpose — signatures are required at this organization, and offering "None" invited accidentally sending an unsigned email. Signature *name* enumeration is real (`OutlookSignatureProvider`/`LocalOutlookSignatureProvider`, added this session) and used by both the Action editor and the ad-hoc email modal. The real Outlook adapter (not built yet) will still need to resolve a selected signature name to actual signature HTML (Outlook stores these under `%APPDATA%\Microsoft\Signatures\`) and append it before sending, since Outlook does not auto-apply a signature to mail sent silently via COM automation (that only happens when a compose window is actually displayed). `EmailSender.send()`'s `signature` param is currently just recorded as a label by the fake.

## Known open items
- Filter engine design (see Design decisions) — the big remaining piece blocking targeted actions and welcome emails from being practically correct; they currently run against the full roster, unfiltered.
- Real Salesforce/Cadence/Outlook adapters not built — everything runs against local fakes today, except Outlook signature *name* reading which is real (see Design decisions).
- Outlook signature resolution (name → actual HTML at send time) not implemented in the (not-yet-built) real `EmailSender` adapter — see Design decisions.
- Two pre-existing test failures, found while testing this session's welcome-email fix but unrelated to it and not yet investigated:
  - `tests/test_views/test_add_action_view.py::test_add_action_view_prioritizes_action_data_group_on_edit` — `AddActionView` doesn't prioritize `action_data`'s assigned group over the nav panel's `initial_group_name` when editing.
  - `tests/test_views/test_update_actions_panel.py::test_refresh_data_updates_state_and_rerenders` — fails when run after other view test files in the same session; looks related to the documented Tk state-pollution issue below but hasn't been root-caused.
- No protection against running multiple app instances at once — plain JSON file storage with no locking, so if two windows are open simultaneously, whichever saves last silently overwrites the other's changes with no warning. This surfaced when repeated app relaunches during a testing session (not a code bug) clobbered a manually-created test group. Unlikely in normal single-window use, but worth keeping in mind.

## Known testing quirks (not app bugs)
- Running `pytest tests/` as one combined invocation sometimes hangs or produces spurious failures — multiple test files each create their own `ctk.CTk()` root in the same process, causing Tk state pollution across CustomTkinter-heavy test files. Scoped runs (e.g. `pytest tests/test_services/`, `pytest tests/test_controllers/`) are reliable; use those instead of chasing failures that only show up in the combined run.
- Running the real app, or tests that instantiate a real `AppController`/`GroupRepository`/`ActionRepository`, writes to the actual `data/templates.json`, `src/data/actions.json`, `src/data/groups.json` — there's no tmp_path isolation for those integration paths yet. Expect these to show as "modified" after manual testing; check the diff before committing rather than assuming it's intentional (see Working rule 7).

## Recently fixed (most recent session)
- Template editor no longer hangs: swapped the pywebview-based editor (broken by a main-thread conflict with CustomTkinter's `mainloop()`) for a `CTkToplevel` modal, rebuilt as a true WYSIWYG editor (`src/services/html_richtext.py`) — bold/italic/underline/highlight/font-size/links render visually instead of as raw tags, with a raw-HTML toggle for HTML-literate professors and formatting-preserving paste from Outlook/Word.
- Template delete button was invisible (an unsupported emoji glyph rendered blank) — fixed. Deleting a template unrelated to the currently-open action now restores that action's own template selection instead of resetting to "New/Custom," and deleting the template *currently assigned* to the open action shows an explicit warning first.
- Added `ActivityLogger`, `StudentDataProvider`/`EmailSender`/`TextSender`/`NoteWriter` (+ fakes), and `ActionRunner` — see Design decisions. Wired into a real `handle_run_action`.
- Added `DashboardView` (new default startup view, nav link next to Settings) with "Send Welcome Emails" and "Send Email to All Students" (ad-hoc WYSIWYG compose via `AdHocEmailModal`).
- `NoteWriter` extended with `update_follow_up_note()` — writing a note now also updates the student's roster-visible follow-up-note field, bundled into the same step (see Design decisions).
- Removed "None" from the Outlook Signature dropdown — signatures are required at this organization; the dropdown now defaults to a real signature instead of inviting an unsigned send.
- Added `OutlookSignatureProvider`/`LocalOutlookSignatureProvider` — reads real Outlook signature names from `%APPDATA%\Microsoft\Signatures\`, replacing the hardcoded fake list in the Action editor's signature dropdown. Extended the ad-hoc "Email to All Students" modal with the same dropdown (it previously had none at all), wired through to `ActionRunner.send_ad_hoc_email`.
- Fixed the welcome-email conflict dialog never firing: `save_action()`'s conflict check read a new action's `id` as `None` (the real UUID wasn't generated until later in the same method), so the group's `welcome_action_id` was silently set to `None` instead of the action's real id. `AddActionView` now generates the real id when the form opens; the "Is Group Welcome Email" checkbox fires the confirm/replace flow live on click (reverting on cancel) instead of deferring to Save, and `populate_fields()` now correctly shows the checkbox checked on reload.
- Fixed a spurious "Switching group will discard changes" dialog appearing after every successful Save: `ScenarioNavPanel._on_group_selected()` was being reused for plain post-save/CRUD display refreshes, which also fired the controller's real group-switch confirmation guard. Split into `refresh_active_group_display()` (no callback — used by save/add/rename/delete) vs. `_on_group_selected()` (fires the callback — reserved for actual user-driven dropdown selections).
- Removed ~22 leftover `print()` debug/click-acknowledgment statements across the controller, views, and `GroupRepository`; migrated the ones with real audit value (action/group CRUD, welcome-flag changes) to `ActivityLogger` so they show up in the Live Application Log instead of only the console.
