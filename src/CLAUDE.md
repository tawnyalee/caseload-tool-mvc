# CLAUDE.md — Action Manager App

## Project overview
Python/CustomTkinter desktop app, rewritten from a previous non-professional dev's spaghetti-code app into a clean MVC design. The app helps professors automate routine student communications (emails, texts, notes) and document them, organized into "Groups" (school courses).

The developer working on this is a C# developer who is newer to Python — favor clear, idiomatic Python and explain any non-obvious language features when they come up.

## Architecture
- `src/models/` — Action, Group, Student, EmailTemplate, and enum definitions. `Student` is a `@dataclass` with 68 fields mirroring the real caseload export (course status, tasks 1-15, mentor info, SAP/CU figures, dates, etc.) on top of the original core fields (`salesforce_id`, `first_name`, `last_name`, `email`, `phone`, `has_signed_up_for_text`); new fields are kept as plain strings on purpose since type-aware filtering is still undesigned (see Filters below). `Student.SALESFORCE_FIELD_MAP` ties each field back to its exact source column name for the real Salesforce adapter to be built later.
- `src/services/` — `ActionRepository`, `GroupRepository`, `TemplateRepository` (JSON file storage); `StudentDataProvider`, `EmailSender`, `TextSender`, `NoteWriter` (abstract interfaces with local `Fake*` implementations — real Salesforce/Cadence/Outlook adapters not built yet, see Known open items); `CsvStudentDataProvider` (reads the roster from a Salesforce report-export CSV instead of the live API — a hedge `StudentDataProvider` implementation for if real Salesforce API access doesn't come through; not wired into `AppController` yet, exists as a tested, ready-to-swap-in fallback — see Design decisions); `csv_student_import.py` (`csv_row_to_student_fields()`/`parse_students_csv()` — the shared raw-CSV-row → Student conversion, used by `CsvStudentDataProvider`, `PlaywrightStudentDataProvider`, and `scripts/convert_sample_csv_to_fixture.py`); `salesforce_browser_session.py` + `PlaywrightStudentDataProvider`/`PlaywrightNoteWriter` (Playwright-based real adapters — API access isn't available at this org, confirmed by other developers doing similar integration work here, so this is the actual integration path, not a hedge — see Design decisions); `SmtpEmailSender` (a TEMPORARY, Gmail-SMTP-based `EmailSender` used only to manually verify the real send pipeline works, ahead of Outlook being available to test against — not the permanent adapter, swap back to `FakeEmailSender` once confirmed); `mongoose_contacts.py` (`MongooseContact`/`load_contacts`/`build_contact_id_map`/`load_and_map`/`MongooseContactIdRepository` — joins a Mongoose contacts/segment CSV export to the roster by phone-then-name to get each student's Mongoose Contact Id, answering the `phone` field's open "Cadence-ID-based texting integration" question from `docs/filter_engine_requirements.md`; scaffolded from researching another WGU-caseload-tool's open-source implementation, see Design decisions); `OutlookSignatureProvider`/`LocalOutlookSignatureProvider` (the one real, non-fake integration so far — lists actual Outlook signature names from `%APPDATA%\Microsoft\Signatures\`, used by both the Action editor and the ad-hoc email modal; `FakeOutlookSignatureProvider` exists for tests); `ActionRunner` (orchestrates running an action, welcome emails, or an ad-hoc send against students, with per-student failure isolation and logging — see Design decisions); `note_records.py` (`NoteInsertRecord`/`resolve_course_code`/`validate_note_record` — the platform-independent "ready for insert" shape for what a note step would eventually write to Salesforce/Learner360, logged on every run for review ahead of the real adapter); `merge_fields.py` (mail-merge token registry — `{{student_name}}`, `{{course_code}}`, `{{last_submitted_task}}`, `{{last_passed_task}}`, `{{next_task}}` — rendered per-student into email subject/body at send time via `ActionRunner._send_email`); `ActivityLogger` (writes to a daily log file and the Live Application Log panel from one call site); `html_richtext` (HTML ⇄ `tkinter.Text` WYSIWYG conversion, used by the template editor and the ad-hoc email compose modal); `name_utils.resolve_first_last_name()` (preferred-name-aware, casing-normalized name resolution — shared by the CSV fixture conversion today and needed again by the real Salesforce adapter later)
- `src/views/` — `AddActionView`, `ScenarioNavPanel`, `DashboardView` (default startup view — three sections: Welcome Emails, an inline "Send Email to All Students" compose area with an identical note section to a regular Action's note step, and Run Action Batch; no `AdHocEmailModal` anymore, that flow moved onto the dashboard itself per developer feedback after manual testing), `TemplateEditorModal`, `BatchRunModal` (HandBrake-style queue for running several actions in sequence — see Design decisions), `ReviewSendModal` (pre-send review/confirm dialog for a single Action run or ad-hoc email — see Design decisions), `merge_field_picker.create_merge_field_menu()` (the "Insert Field" dropdown, reused across every place email content is drafted), `MultiReviewSendModal` (pre-run review/confirm dialog for batch runs and welcome emails, grouped by course code/item — see Design decisions), `FilterRow`/`DatePickerEntry` (the filter-builder UI), and other CustomTkinter views
- `src/controllers/app_controller.py` — main app controller
- `Sample.csv` (repo root) — a real, PII-masked export of caseload fields (252 rows, real column names/shapes) the developer provided for building out realistic fake data and eventually the filter engine. `scripts/convert_sample_csv_to_fixture.py` regenerates `data/fake_students.json` from it (rerun manually whenever `Sample.csv` changes); `FakeStudentDataProvider` itself only ever reads the JSON output, not the CSV. One row was dropped (see docs/filter_engine_requirements.md) for genuine source-data corruption; `LatestCourseNote` was dropped entirely as an unneeded field.

## Working rules (follow these strictly)
1. **One focused change at a time.** Propose a single change with reasoning and a specific test to verify it, then wait for the result before moving on to the next thing.
2. **Always ask for the actual current code** before proposing changes to a file that's had prior edits — don't assume you remember its state; read the file fresh.
3. **Ask about intent (what SHOULD happen) vs. observed behavior** before proposing a fix — don't assume the cause.
4. **Preserve existing variable/field names and structures** unless they're actively misleading. Ask before renaming anything.
5. **ID-based lookups only.** Never write new code that looks up records (groups, templates, actions, or any future entity) by name — names can be renamed mid-session. Always use the record's stable ID.
6. **Name secondary issues, don't fix them.** If you spot an unrelated bug or issue while investigating something else, mention it but don't fix it until the current task is finished.
7. **Git safety net.** The developer is still learning Git. Proactively remind them when it's a good time to commit or branch (e.g. before starting a risky change, after a working milestone) — don't assume they'll remember to do it themselves. Also watch for real data files (`data/*.json`, `src/data/*.json`) picked up as "modified" from manual testing — confirm with the developer before including those in a commit; they're usually test noise, not intentional changes.

## Design decisions (settled — don't re-litigate without new input from the developer)
- **Resource access is abstracted behind interfaces** (`StudentDataProvider`, `EmailSender`, `TextSender`, `NoteWriter`), each with a local `Fake*` implementation backing everything today (`data/fake_students.json` plus in-memory records). Real Salesforce/Cadence/Outlook adapters implement the same interfaces later; nothing that calls them needs to change.
- **The app must stay platform-independent of Salesforce specifically** — the developer expects to migrate from Salesforce to a different platform ("Learner360," Salesforce-based but distinct) in roughly a year, and wants the app's logic to work "regardless of where the data comes from." This is why `Student`'s field names (`momentum`, `course_code`, etc.) are the app's *own* naming scheme rather than Salesforce's raw field/API names, and why `Student.SALESFORCE_FIELD_MAP` is treated as a Salesforce-adapter-specific detail, not something baked into `Student` itself or any app logic (filters, `ActionRunner`, views). A future Learner360 adapter would implement `StudentDataProvider` and carry its own separate field map (e.g. `LEARNER360_FIELD_MAP`) translating into the same `Student` shape — nothing else in the app should need to change. Keep this in mind for any future field mapping or data-provider work: don't let Salesforce-specific naming or assumptions leak past the adapter boundary.
- **Running an action (`ActionRunner.run`):** email and text are attempted independently per student (one failing doesn't block the other). A note step — writing the interaction note *and* updating the student's roster-visible follow-up-note field, bundled as one unit — runs only if the **email** succeeded; otherwise it's skipped and logged, not attempted. **Texts never trigger a note** (changed 2026-10-13, developer's call): Mongoose writes its own note for every text at the end of the day, so a text-only action has no note step at all (logged once per run), and a text succeeding while the email fails still skips the note. The follow-up field fails only if the Salesforce save itself fails, and that failure is logged per student for manual handling. One student's failure never stops the run — every step (success/failure/skip) is logged via `ActivityLogger` and rolled into a final succeeded/failed/skipped summary.
- **Welcome emails (`ActionRunner.run_welcome_emails`, the Dashboard's "Send Welcome Emails" button):** deliberately no separate course/student-matching logic in the app. It just runs whichever action is marked as each group's `welcome_action_id` (already existing on `Group`) through `ActionRunner`, using whatever filter the professor configured on that action themselves. This was a deliberate simplification to avoid building course-mapping or "new student" detection logic in the app.
- **Dropped:** a "new students since last checked" dashboard count. Considered, then abandoned in favor of professors using their own filter criteria (e.g. "Follow Up Note Is Empty") on their welcome action — no local "last checked" state needed. Don't resurrect this without the developer asking.
- **Filters are NOT implemented yet.** `StudentDataProvider.get_students()` and everything downstream currently act on the full roster unconditionally — filters stored on an `Action` are not applied anywhere. The developer is still working out real-world filter requirements (field-type-aware operators, AND/OR grouping, relative dates, "Is Empty"/"Is Not Empty") from how they actually use Salesforce's own filters today. Don't design or guess at a filter engine without that input — ask.
- **Pre-send review dialog (`ReviewSendModal`, single-item version):** every single Action run and ad-hoc email now pauses on a review-and-confirm dialog before anything sends - nothing goes out until the professor clicks Send in it. Shows "0 students currently meet these conditions" (no list/send controls) when nothing matches. Otherwise: a checkbox list of matching students (name + ID, all checked by default, Select All/None), and - only when the send includes email - an editable subject/body (pre-filled from the Action/draft, rendered via the same `html_richtext` WYSIWYG helpers the template editor uses, no formatting toolbar) plus a note that merge fields personalize per student. Edits here are a one-time override for this send only - `ActionRunner.run()`/`send_ad_hoc_email()` accept optional `included_student_ids`/`email_subject_override`/`email_body_override` that layer on top of the Action/template's own saved content without touching it. `ActionRunner.get_matching_students(action)` exists so the dialog can show the filter-matched list before anything runs. Every run also now logs `'<Action Name>' is currently running for <N> students` plus a `[PROCESSING] <name> (ID: <id>)` line per student as it goes, in the Live Application Log.
- **Mail-merge personalization (`merge_fields.py`):** exactly 3 concepts, exposed as 5 tokens, chosen by the developer rather than exposing the full filter-field registry (drafting an email is a different concern from filtering the roster). `{{student_name}}` and `{{course_code}}` are direct. Task position is split into three because "last submitted" and "last passed" are genuinely different numbers when a student's latest submission needs revisions: `{{last_submitted_task}}` (highest submitted `task_N`, regardless of status), `{{last_passed_task}}` (**blank**, not a guess, unless the student's most recent submission was itself a pass — there's no per-task pass/fail history in this data, only the status of whichever task is latest, see `task_utils.py`), `{{next_task}}` (one past the last submitted task, or `Task 1` if nothing's submitted yet, blank once past Task 15). Rendered per-student via `render_merge_fields()`, called from `ActionRunner._send_email` for both `is_email` Action runs and ad-hoc email — an unrecognized `{{token}}` is left as literal text, not an error, since it might be intentional. An "Insert Field" dropdown (`src/views/merge_field_picker.py`) is wired into every place email content is drafted (`TemplateEditorModal`'s toolbar for the body, `AddActionView`'s subject field, `DashboardView`'s ad-hoc subject/toolbar) — it inserts the token at the cursor, same reset-after-use pattern as the template editor's font-size menu. Deliberately NOT wired into note/text fields yet — no backend rendering exists for those, and the ask was specifically about email.
- **Pre-send review dialog (`MultiReviewSendModal`, multi-item version):** covers batch runs and welcome emails - both fire across several (Action, group) pairs in one operation, so a per-item confirm like `ReviewSendModal` would mean confirming multiple times per batch. Instead: one dialog, one section per item (course code/group + action name as the header, e.g. "D424 — Welcome Action"), each section independently deselectable (per-section Select All/None) - explicitly NO editable email content here, the developer's call: if an item's email needs editing, that's done on the Action itself beforehand, not in this dialog (may change in a future release). A section with 0 matching students just shows "0 student(s)" with no checkboxes rather than blocking the rest. Confirming hands back a `{item_key: {selected_ids}}` dict - `str(index)` keys for batch (`ActionRunner.run_batch`'s new `included_ids_by_index`, keyed by position since the same action could appear twice against different groups), `group.id` keys for welcome emails (`run_welcome_emails`'s new `included_ids_by_group_id`). `handle_send_welcome_emails` only builds a review section for groups with both a `welcome_action_id` set AND a matching real action (silently skips groups with no welcome action or a dangling reference, same as `run_welcome_emails` always has). Same defensive layout lesson from `ReviewSendModal` applied from the start: the Cancel/Run button row is packed `side="bottom"` before the scrollable item sections are built, so it can never get pushed out of view.
- **Salesforce integration plan (revised 2026-09-01, then again same day once the real blocker was found): API access is not viable at this org — Playwright browser automation is the actual integration path, not a hedge.** The developer confirmed via `scripts/test_salesforce_connection.py` (username/password/security-token login, `simple-salesforce`) that login fails with a generic `INVALID_LOGIN` error even with correct credentials and the right custom-My-Domain host (`<name>.my`, not the `.lightning.force.com` UI domain — `simple_salesforce` builds its login URL as `https://{domain}.salesforce.com/...`, so only the bare My Domain name goes in `SF_DOMAIN`). Ruled out: empty/blank env vars, wrong domain, account lockout (the developer can still log in normally elsewhere). The org has MFA enabled, and other developers independently doing similar integration work at this org confirmed they also had to fall back to browser automation — API access appears to be blocked at an org policy level, not an account-specific fix. `scripts/test_salesforce_connection.py` and `CsvStudentDataProvider` (the original hedge) are kept since they're still valid/tested, but the live path forward is:
  - **Login: the session is kept in memory only, asked for on every app launch** (2026-10-22). **Clarified 2026-10-28 by the developer:** the rule is that *the app* never stores credentials, not that the browser must forget the device. A blank profile on every login made PingID treat each launch as a new device, so login windows now use the app's own saved Edge profile (`browser_launch.launch_login_context`, `launch_persistent_context` on `app_paths.browser_profile_dir()` = `%LOCALAPPDATA%\CaseloadTool\edge-profile`). Whether Edge remembers the password is the professor's choice. After login, `clear_cached_pages` drops the target site's HTTP cache and site storage (keeping cookies) so the Caseload page/roster doesn't sit in Edge's cache (FERPA). Only one login window at a time (Edge locks the profile; a plain message says so). The hidden roster/note browsers are unchanged: blank contexts loaded with the in-memory `storage_state`. `src/services/salesforce_browser_session.py`'s `log_in_interactively()` opens a visible browser at `CASELOAD_APP_URL`. The professor logs in themselves (password + PingID MFA; the app never sees either). "Logged in" means `EXPORT_BUTTON_SELECTOR` is visible, so a redirect mid-SSO can't count as success. The window times out after 5 minutes. The cookies (`storage_state()` as a dict) stay in a module-level variable for this app session, and both `PlaywrightStudentDataProvider` and `PlaywrightNoteWriter` open hidden browsers with them. `AppController._refresh_caseload_at_startup` logs in, then loads the roster. On failure the app still opens, and a popup explains (it used to go only to the log file, because the window doesn't exist yet at that point). "Refresh Caseload" logs in if needed, and logs in again once on `SessionExpiredError`. `scripts/salesforce_login.py` and the saved `data/.salesforce_session.json` were **deleted**. Background: the previous file-based session (saved 2026-09-03) is why live testing never showed a login, and its silent expiry on 2026-10-22 is what surfaced this. **Testing safeguard:** `tests/conftest.py` makes any test that tries to open a *visible* login window fail immediately. This happened once, when older tests started reaching the new startup login. **Login needs PingID on the professor's phone.** As of 2026-10-22 the developer's new phone isn't enrolled, so nothing Salesforce-backed can run until it is. **Mongoose was converted to the same in-memory pattern the same day** (`mongoose_browser_session.py`; `scripts/mongoose_login.py` deleted). Its `log_in_interactively()` takes `logged_in_selector` from the caller, because what proves you're logged in to Mongoose isn't known yet; capture it during the Mongoose codegen session.
  - `PlaywrightStudentDataProvider` (`student_data_provider.py`): loads the saved session, drives a real browser to a report/export page, clicks Export, downloads the CSV, and parses it with the exact same `csv_student_import.parse_students_csv()` the CSV hedge uses — browser automation only replaces the manual-export step, not the parsing. **Confirmed working live 2026-09-03** against `CASELOAD_APP_URL` + `EXPORT_BUTTON_SELECTOR` (234 students, all with email/course_code, 175/234 with phone — the exact blank-phone gap `mongoose_contacts.py` exists to work around) and **wired into `AppController`**, wrapped in `CachingStudentDataProvider` (below). Two hardening fixes made during this pass: (1) the downloaded roster CSV's temp dir is now deleted right after parsing (`shutil.rmtree` in a `finally`) — per the developer's explicit FERPA constraint, real student PII must never linger on disk; it wasn't being cleaned up before. (2) an expired saved session gets redirected to WGU's SSO login instead of the report page — previously this just hung the `page.click()` for a bare 30s Playwright `TimeoutError` with no hint what was wrong (this happened live: the developer tried to log in through the popped-open browser mid-run, and the script's `finally: context.browser.close()` fired while they were still typing their password, closing the window on them). Now `_looks_like_a_different_host()` (a pure, unit-tested helper) detects the redirect immediately after `page.goto()` and raises a clear "session expired, run scripts/salesforce_login.py" `RuntimeError` instead.
  - **`CachingStudentDataProvider` (`student_data_provider.py`) wraps the real provider — required, not optional.** Several call sites each independently call `get_students()` in normal use (a single Action's review dialog, EVERY item in a batch review, running an action) — confirmed live that a bare `PlaywrightStudentDataProvider` would mean a batch review of N actions triggers N separate ~20s+ live browser round trips back-to-back. The cache fetches once and reuses that snapshot until `.refresh()` is called explicitly (wired to "Refresh Caseload", see below) or `_refresh_caseload_at_startup()` fires (`AppController._load_data`, every launch). **FERPA constraint (explicit, from the developer, 2026-09-03): no student data may persist across app sessions** — the cache is deliberately in-memory only, nothing here is ever written to disk, and it was the developer's own suggestion that a temp-file-deleted-every-session approach would also be acceptable if ever needed, but in-memory trivially satisfies the constraint with less code. A failed `.refresh()` leaves whatever was cached before untouched (doesn't wipe a good roster on a bad retry) — the *first* fetch failing leaves the cache `None`, so the next `get_students()` call retries rather than getting permanently stuck.
  - **Startup behavior — eager fetch on every launch, the developer's explicit choice** over a lazy first-use fetch, because the roster changes throughout the day at the source (this is also why "Refresh Caseload" exists as a real button, not just a cache-primer). `AppController._refresh_caseload_at_startup()` (called from `_load_data`, split into its own method specifically so tests can patch it out the way they already patch `_init_views`, instead of every real-`AppController()` test triggering a live Salesforce round trip) does this; a failure here is logged, not raised — the app must still start usably even with an expired/missing session, and "Refresh Caseload" is the retry path. "Refresh Caseload" (`handle_refresh_requested`) is a real button now, not a stub (see Known open items) — calls `.refresh()`, shows the new student count on success or the error on failure.
  - `PlaywrightNoteWriter` (`note_writer.py`): same saved-session pattern, navigates to a student's record page. The actual click/fill sequence for writing a note or updating the follow-up field is NOT hardcoded — it's supplied as `write_note_fn`/`update_follow_up_fn` callbacks at construction time, since the real Salesforce page layout (which button, which field, inline-edit vs. modal) isn't known yet and guessing wrong selectors would be worse than being explicit about what's still needed. Once the real page is visible, `python -m playwright codegen <url>` records the real interaction to turn into a callback.
  - **Both classes take their target URLs/selectors as constructor arguments, not hardcoded constants — this is deliberate**, per the developer's explicit ask: "build whatever will work with Salesforce but easily switch to the in-house app later" (referring to a WGU-internal system at `learner360.wgu.edu/caseload`, distinct from raw Salesforce Lightning — confirmed to be a subdomain of `wgu.edu`, not the third-party `learner360.ai`). Swapping automation targets later is different constructor arguments (or a sibling class), not a rewrite of `ActionRunner`/`AppController` — same platform-independence principle as the `StudentDataProvider`/`NoteWriter` interfaces themselves.
  - `PlaywrightNoteWriter` is now wired into `AppController.__init__` (as `self.note_writer`, replacing `FakeNoteWriter`) — **the first real, non-fake adapter actually running through the app**, done 2026-09-02 as a deliberate readiness-check pass (see "Production readiness" below) after the developer confirmed via manual testing that everything built so far — filters, review flows, batch runner, Saved Batches — works correctly. `StudentDataProvider`/`EmailSender`/`TextSender` are still fakes. Construction never fails even without a saved Salesforce session; `write_note()`/`update_follow_up_note()` raise a clear "run `scripts/salesforce_login.py` first" `RuntimeError` at call time instead, which `ActionRunner` already catches and logs per student like any other failure — so wiring it in unconditionally is safe regardless of login state. **Update 2026-09-02: the real callbacks are now built, captured via `python -m playwright codegen` against the actual org, and confirmed working end-to-end against production Salesforce** — see `src/services/salesforce_callbacks.py` (`write_note_fn`, `update_follow_up_fn`, `CASELOAD_APP_URL`, `EXPORT_BUTTON_SELECTOR`) and `scripts/test_note_writer_live.py` for the live-test harness. Notable gotchas that cost real debugging time, worth remembering:
    - The roster is a large (~242 students), virtualized grid — a row that isn't currently scrolled into view doesn't exist in the DOM at all yet, and which student ends up where isn't predictable (the roster reshuffles daily). `_row_for_student()` handles this by setting `scrollTop` directly on the nearest actually-scrollable ancestor of a row (found by walking up the DOM) until the target row appears — a plain mouse-wheel scroll didn't move anything on this custom grid, matching the developer's confirmation that they scroll it by dragging the scrollbar, not the wheel.
    - Two form fields (the course-code typeahead in `write_note_fn`, and the follow-up-note textarea in `update_follow_up_fn`) only work with `press_sequentially()` (real, per-character simulated typing) — `.fill()` sets the value in one shot with no real keystrokes, and Salesforce's own JS search/save logic on both fields never notices a `.fill()`-set value at all. This one is easy to reintroduce by accident in any future Playwright automation here — default to `press_sequentially()` for anything Salesforce needs to actively react to as you type.
    - The follow-up note saves on blur (losing focus to a click elsewhere), not on any particular key — clicking the row's own ID cell afterward is a safe, side-effect-free way to trigger that.
    - Title-text-based element lookups need to be exact and complete, not a hoped-to-be-unique substring — an earlier attempt at `get_by_title("Add followup note for this")` (a truncated guess) turned out to also match a *different* column's similarly-worded control. The real, complete title (confirmed via DevTools) is "Add followup note for this student and course".
- **Mongoose texting integration — login/session infrastructure built 2026-09-03, real send automation not yet started.** `src/services/mongoose_browser_session.py` mirrors `salesforce_browser_session.py`: a completely separate login (Mongoose is its own site), done interactively by the professor and kept **in memory only** (converted 2026-10-22; nothing saved to disk). **Architecture decided (2026-09-03, explicit developer call):** the first real Mongoose `TextSender` will send **one text per student**, matching the existing `TextSender.send(to_phone, subject, body)` interface exactly — no changes to `ActionRunner`/the interface. The reference project's more efficient department/timezone-batched compose model was explicitly deferred, not rejected — revisit only if per-student sends prove too slow in practice, not preemptively. Still needed before a real adapter can be built: (1) a `playwright codegen` recording of the developer actually composing/sending a real text in this org's Mongoose, since the reference project's DOM selectors are unconfirmed here (same "guessing wrong is worse than being explicit" lesson as Salesforce); (2) confirming whether this org's Mongoose also forces scheduling instead of immediate send (the reference org can't send instantly — likely a Mongoose-platform constraint, not org-specific, but unconfirmed).
- **Cross-project research background (scaffolding started via reading another project's code, not yet a live adapter):** The developer pointed at another open-source WGU caseload-automation tool (`github.com/ashejim/caseload-tool`, same institution, same Salesforce Caseload App page and the same Mongoose/Cadence texting platform) to see how it solved the same integration problems. The developer's explicit scope call: borrow ideas relevant to general outreach automation (notes/email/text), not that project's broader feature set (its own caseload viewer, Momentum/success-path calibration, action queue, etc.) — those are out of scope here, don't pull them in. The developer has used that project's texting feature daily, for weeks, as their actual working tool — their complaint with that project is UI/UX polish (clunky, hard to find things), not the texting logic, which they call solid. That's production-level validation of the Mongoose Contact-Id join strategy below, not just a read of their source. Two takeaways so far:
  - **Salesforce automation:** their `note_form.py`/`browser.py` hit the identical virtualized-grid, `.fill()`-doesn't-fire-JS, and blur-to-save issues this app's `salesforce_callbacks.py`/`salesforce_browser_session.py` already solved (same org). Theirs is more defensive in ways this app wasn't — poll-before-read on Submit-enabled state, click-then-verify-it-stuck retries, a three-tier click fallback for elements a slide-out sidebar can render outside Playwright's clickable area, and **screenshot-on-failure**. Of those, only **screenshot-on-failure was ported** (`_screenshot_failure` in `salesforce_callbacks.py`, saving to `logs/screenshots/` — already gitignored via the existing `logs/` entry — and wrapping both `write_note_fn`/`update_follow_up_fn` in try/except so any failure raises a `RuntimeError` naming the student id, the screenshot path, and the underlying error; `ActionRunner._handle_note_step` already catches `Exception` generically and just logs `str(exc)`, so this is a pure improvement to that logged message with no behavior change on success). The other three patterns (retry-until-verified clicks, poll-before-read, force-click fallback) were deliberately **not** ported — they'd change click/timing behavior on a sequence that's already confirmed working end-to-end against production, and there's no way to verify a change to that sequence without a live run. ## Known testing quirks (not app bugs)
- Running `pytest tests/` as one combined invocation can still produce spurious failures (e.g. a `TclError` mid-run) — multiple test files each create their own `ctk.CTk()` root in the same process, causing Tk state pollution across CustomTkinter-heavy test files. Scoped runs (e.g. `pytest tests/test_services/`, `pytest tests/test_views/`) are reliable; use those instead of chasing failures that only show up in the combined run. Note: a test failure that merely *shows up* in a combined run isn't necessarily caused by this — `test_refresh_data_updates_state_and_rerenders` was previously (mis)attributed to this quirk but turned out to be a real, deterministic logic bug reproducible in complete isolation (see Recently fixed). Confirm a failure reproduces standalone before writing it off as Tk pollution.
- **Resolved 2026-10-22: tests no longer touch real data.** `tests/conftest.py` gives every test its own temporary data folder (`CASELOAD_DATA_DIR`), so a real `AppController`/repository in a test writes to a temp dir. Before this, those tests wrote straight into the real `src/data/*.json`.
- **A test on a real `AppController()` that doesn't mock EVERY `messagebox.show*`/`ask*` call its code path can reach will hang forever, not fail** — a real, un-mocked `tkinter.messagebox` call opens an actual native OS dialog and blocks on a real human click. Found live 2026-09-03: `test_save_action_sets_welcome_action_id` and three siblings had always been missing a `messagebox.showinfo` patch on `save_action()`'s unconditional final call, but it only started actually hanging that session (previously the desktop session wasn't active/interactive enough for the dialog to truly block) — so "it passed before" is not proof a test correctly mocks every reachable messagebox call, only that the desktop happened to be in a state where it didn't matter that session. If a test on a real `AppController()` (or a `MagicMock()` controller running a real unbound method via `.__get__`) ever hangs with no error, suspect this first — not a real deadlock. `pytest-timeout` (`pip install pytest-timeout`, then `pytest ... --timeout=15`) turns a silent hang into a clean stack trace pointing at the exact unmocked call, which is how these were actually found — much faster than binary-searching decorators by hand. Not currently in `requirements.txt`/pinned anywhere; worth adding permanently if this class of bug recurs.
- **Module-identity trap extends to `@patch.object`/`isinstance()` on classes, not just `@patch("string.path")`** — this test file imports `AppController` via `controllers.app_controller` (no `src.` prefix, see the `sys.path.insert` at the top and the existing `BatchRunModal` comment on `test_handle_open_batch_runner_loads_actions_and_opens_modal_with_on_run_wired`), which means anything `app_controller.py` itself imports via `from src.services.X import Y` is a *different* class object than the same `Y` imported here via `from services.X import Y` — Python loads the same file twice under two different module names. Found live 2026-09-03: new tests imported `PlaywrightStudentDataProvider` via `services.student_data_provider` (matching this file's existing `AppController` import style) and got silent, no-error failures — `@patch.object(PlaywrightStudentDataProvider, "get_students")` patched the *wrong* class, so the REAL method ran, making real live Salesforce calls during a supposedly-mocked unit test (confirmed by real student PII showing up in the assertion failure diff). Fix: import anything used with `@patch.object`/`isinstance()` against an `AppController`-internal object via the *same* `src.`-prefixed path `app_controller.py` itself uses (`from src.services.student_data_provider import ...`), not the bare `services.X` path used for `AppController` itself. String-based `@patch("exact.module.path.Name")` doesn't have this problem *as long as the string path matches where the code under test actually looked the name up* — but object-identity patching (`@patch.object`) and `isinstance()` checks are never safe unless both sides import through the identical module path.
